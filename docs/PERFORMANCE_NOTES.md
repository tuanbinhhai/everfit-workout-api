# Performance Notes

Step 12 performance verification: does the read/write path hold up at 50,000+
workout entries for one user, backed by real evidence (`EXPLAIN (ANALYZE,
BUFFERS)` against real Postgres), not just "an index exists so it must be
fine"?

All numbers below are **local benchmark observations on one developer
laptop**, a single Postgres connection, no concurrent load, and no network
latency beyond localhost. They are not production capacity claims and no load
test was run — see [Limitations](#limitations).

## 1. Environment

- PostgreSQL 16.15 (aarch64, Alpine, `postgres:16-alpine`), via Docker Compose, host port 5433
- API: Docker container built from the project `Dockerfile` (`node:22-slim`), host port 3000
- Host: developer laptop (Apple Silicon / aarch64), no other load during measurement
- Prisma 7.10.0 with the `@prisma/adapter-pg` driver adapter

## 2. Dataset shape

Generated by `scripts/seed-scale-test.ts` (`npm run perf:seed`):

- **50,000** `workout_entries` for one user (`perf-user`), **199,999**
  `workout_sets` (avg. ~4 sets/entry, range 3–5)
- A deliberately worst-case, skewed exercise distribution — not a uniform
  distribution — to stress-test the single-exercise-concentration cost model
  from `docs/ARCHITECTURE.md` §5.2:
  - Bench Press: 20,000 entries (40% of the dataset)
  - Squat, Deadlift, Incline Bench Press, Barbell Row, Overhead Press, Bicep
    Curl, Leg Press, Lat Pulldown: 3,750 entries each
  - Leg Press and Lat Pulldown are deliberately **not** present in
    `exercise_muscle_groups`, to exercise the muscle-group-filter path when
    some exercises have no mapped muscle group
- Dates span 730 days (~2 years) back from 2026-09-15, deterministically
  distributed by entry index (no gaps-free guarantee, but full spread)
- Units alternate: 1 in 7 entries uses `lb` (converted via the real
  `UnitConversionService`), the rest `kg`
- A second user (`perf-user-2`) gets 200 Bench Press entries, for isolation
  (its rows must never leak into `perf-user`'s query results)
- `exercise_muscle_groups` is untouched by the seed script — it's the normal
  7-row static/dev table, not part of the perf dataset

Generation is **deterministic** (pure index arithmetic, no RNG), batched in
groups of 2,000 via `createManyAndReturn`/`createMany` (never one row at a
time, never through the HTTP API), and guarded against accidental re-seeding
on top of existing perf data.

Commands:

```
npm run perf:seed     # generate the dataset (idempotent-guarded, ~11s)
npm run perf:explain  # run ANALYZE + all benchmark scenarios below
npm run perf:clean     # delete perf-user / perf-user-2 rows only
```

These are **not** part of `npm test` and do not run in CI; the perf dataset
lives only in the local dev Postgres volume and is never committed.

Actual seed run: 50,200 entries / 200,799 sets inserted in **11.2s**.
Post-seed row counts were independently re-verified with a direct `psql`
query (not just the seed script's own console output):
`perf-user` → 50,000 entries / 199,999 sets; `perf-user-2` → 200 entries;
`exercise_muscle_groups` → 7 rows (unchanged).

## 3. Schema / indexes in scope

```
workout_entries:
  workout_entries_pkey            UNIQUE btree (id)
  idx_entries_user_date           btree (user_id, date DESC, id DESC)
  idx_entries_user_exercise_date  btree (user_id, exercise_name_normalized, date DESC, id DESC)
  idx_entries_exercise_trgm       GIN (exercise_name_normalized gin_trgm_ops)

workout_sets:
  workout_sets_pkey               UNIQUE btree (id)
  idx_sets_entry                  btree (workout_entry_id)
  uq_sets_entry_set_index         UNIQUE btree (workout_entry_id, set_index)

exercise_muscle_groups:
  exercise_muscle_groups_pkey     UNIQUE btree (exercise_name_normalized)
```

Before measuring, `ANALYZE workout_entries, workout_sets,
exercise_muscle_groups;` was run explicitly so the planner isn't working off
stale statistics.

## 4. Methodology

`scripts/explain-queries.ts` (`npm run perf:explain`) enables Prisma's
query-event logging (`log: [{ emit: 'event', level: 'query' }]`), calls the
**real repository methods** (`WorkoutsRepository.findHistory`,
`PersonalRecordsRepository.findCandidates`, `PrismaMuscleGroupProvider`),
captures the exact SQL + parameters Prisma actually sent, and re-runs that
same SQL wrapped in `EXPLAIN (ANALYZE, BUFFERS)`. This avoids hand-guessing
what the ORM "should" generate.

Two real bugs were found and fixed while building this harness (see
`AI_WORKFLOW.md` for the full writeup):

1. `findHistory()` uses Prisma's `include: { sets: ... }`, which issues **two**
   separate SQL statements (one for `workout_entries`, one for the batched
   `workout_sets` lookup). The first version of the script only explained the
   *last* captured query, silently explaining the wrong (sets) statement for
   every history scenario.
2. After fixing that, explaining multiple queries per scenario meant the
   script's own `EXPLAIN` calls were themselves captured by the same
   `$on('query', ...)` listener, corrupting the iteration mid-loop
   (`EXPLAIN EXPLAIN ...` syntax errors). Fixed by snapshotting the captured
   list before iterating it.

All results below are from the corrected script.

A third real issue surfaced while cleaning up after benchmarking, worth
recording here since it directly affects how this workflow must be run in
the future:

- Every e2e/integration spec's `beforeEach` calls an **unscoped**
  `prisma.workoutSet.deleteMany()` / `prisma.workoutEntry.deleteMany()` for
  its own test isolation — not filtered to that test's own user id. Running
  `npm test:integration` / `npm run test:e2e` while the perf dataset exists
  wipes it entirely, as a side effect, before any perf-specific
  investigation happens. In this session that's harmless (all `EXPLAIN`
  evidence and the write-path check were already captured before the
  regression suite ran), but it means the perf dataset must be **seeded
  after** running the regression suite, not left in place across it, and
  `npm run perf:seed` must be re-run before any future `npm run perf:explain`
  session if the regression suite ran in between.
- `scripts/seed-scale-test.ts` originally called `main()` unconditionally at
  module load, with no `require.main === module` guard. Since
  `clean-scale-test.ts` and `explain-queries.ts` both import `PERF_USER` /
  `PERF_USER_SECONDARY` from it, merely importing those constants triggered a
  full seed attempt as a side effect. Combined with the point above, this
  caused a real, observed failure: a `perf:clean` run found 0 rows (already
  wiped by the regression suite that ran just before it — see above), so the
  seed side-effect's own existence guard did **not** short-circuit, and it
  silently re-inserted a fresh 50,200-row dataset in the middle of what was
  supposed to be a cleanup run. Fixed by gating `seed-scale-test.ts`'s
  `main()` call behind `if (require.main === module)`.

## 5. History — base case (`GET /workouts`, first page, limit=20)

Entries query: `Index Scan using idx_entries_user_date`, `Index Cond:
(user_id = 'perf-user')`, no filter, no sort needed (index already delivers
`date DESC, id DESC` order). **21 rows** (limit+1 for `hasMore`), 24 buffer
hits, **0.021ms**.

Sets query (batched `workout_entry_id IN (...)`): `Index Scan using
idx_sets_entry`, 64 buffer hits, **0.042ms**.

Interpretation: exactly the expected shape — index gives sorted output
directly, no `Sort` node, cost dominated by nothing (sub-millisecond).

## 6. History — deep cursor page (~25,000 rows in, limit=20)

Entries query: `Index Scan using idx_entries_user_date`, `Index Cond:
(user_id = 'perf-user')`, but the cursor's OR-shaped predicate (`date <
$cursor OR (date = $cursor AND id < $cursor_id)`) is applied as a **`Filter`**,
not folded into the index condition. **25,001 rows removed by filter**,
25,177 buffer hits, **2.858ms**.

Interpretation (real finding, not assumed): the composite index still avoids
a full table scan and avoids a `Sort` (rows come out pre-ordered), but the
OR-form cursor predicate can't be expressed as a single-value index bound
beyond the `user_id` equality prefix — Postgres walks the index in order from
the start and filters out everything before the cursor position. Cost is
therefore **proportional to how deep the cursor is**, not O(1). At this
dataset size (50k rows, cursor 25k deep) that's still fast (under 3ms), but
it would keep growing roughly linearly with cursor depth on a much larger
single-user history. No change made — 2.858ms is well within acceptable
latency for the current scale and this wasn't flagged as a problem by any
concrete measurement; documenting it here as a known characteristic for
future reference.

(The cursor value used here was located via a **benchmark-only**
`OFFSET 25000 LIMIT 1` query — clearly not how the app paginates in
production, used solely to obtain a realistic deep cursor for this test.)

## 7. Partial exercise search (`exerciseName=bench`, limit=20)

`Index Scan using idx_entries_user_date`, `Index Cond: (user_id =
'perf-user')`, `Filter: (exercise_name_normalized ~~ '%bench%')`, 36 rows
removed by filter, 60 buffer hits, **0.026ms**.

Interpretation (checked, not assumed): the `pg_trgm` GIN index
(`idx_entries_exercise_trgm`) is **not used** for this query. The planner
instead scoped by `user_id` via the composite B-tree index and applied the
substring match as a cheap `Filter`, because `LIMIT 20` combined with
`user_id` selectivity (50k rows) makes that plan cheaper than a GIN bitmap
scan across a potentially much larger exercise-name match set spanning all
users. This is the correct planner call for this data shape — the trigram
index still gets genuine use elsewhere (§9).

## 8. Combined filter (partial exercise + 60-day date range, limit=20)

`Index Scan using idx_entries_user_date`, `Index Cond: (user_id = 'perf-user'
AND date >= ... AND date <= ...)`, `Filter:
(exercise_name_normalized ~~ '%bench%')`, 36 rows removed by filter, 60
buffer hits, **0.027ms**. Same shape as §7 — date range folds into the index
condition, substring stays a filter. No trigram index use here either, and
none needed at this cost.

## 9. Muscle-group filter (via the configurable provider)

`listExerciseNames('chest')` → `["bench press", "incline bench press"]` in
**~0ms** (`Seq Scan` on the 7-row `exercise_muscle_groups` table — correct
choice for a table this small; no index needed or used).

History query with `muscleGroup=chest` resolves to `exercise_name_normalized
IN ('bench press', 'incline bench press')`: `Index Scan using
idx_entries_user_date`, filter applies the `IN` list, 60 buffer hits,
**0.027ms**. Same shape as the substring case — expected, since it's
structurally the same kind of predicate over the same index.

## 10. Personal records — all-time, worst-case exercise (bench press, 20,000 entries / ~80,000 sets)

This is the query `docs/ARCHITECTURE.md` §5.2 explicitly predicts should cost
**proportional to the candidate set**, not O(1) — this run is the direct
evidence check for that claim.

- Candidate lookup: `Bitmap Index Scan using idx_entries_exercise_trgm`,
  `Index Cond: (exercise_name_normalized = 'bench press')` — the `pg_trgm`
  GIN index **is** used here (for an equality predicate; `gin_trgm_ops`
  supports `=` as well as `LIKE`/`ILIKE`), recheck + `user_id` filter narrows
  20,168 candidates down to 20,000 rows, 380 buffer hits, ~4.6ms of the total.
- Hash-joined against `workout_sets` (`Seq Scan`, 1877 buffer hits, all
  200,802 rows — cheap relative to the rest) to build the ~80,000-row
  candidate set.
- **Three separate sorts** (one per metric: max weight, volume, Epley 1RM),
  each over ~80,000 rows, each spilling to disk (`Sort Method: external
  merge`, ~4–5.5MB each) because the default `work_mem` isn't large enough to
  sort that many rows in memory.
- Total: 2,257 shared buffer hits + ~3,300 temp blocks read/written,
  **156ms** execution time.

Interpretation: **confirms** the architecture's cost model — cost scales with
candidate-set size (proportional to how many times a user logged this
exercise), not O(1). 156ms for the single worst-case exercise across the
entire 50k-entry dataset (40% concentration, an intentionally pathological
scenario — a real user doing one exercise 20,000 times is far outside
realistic usage) is within acceptable bounds for an infrequent, single-lookup
endpoint. No query/schema change made. If this path is ever shown to be a
real bottleneck (e.g., evidence of exercises with tens of thousands of real
entries), a bounded top-N rewrite (three `ORDER BY ... LIMIT 1` queries
instead of `ROW_NUMBER()` over the full set) is the natural next step, since
Postgres can satisfy a bounded `ORDER BY ... LIMIT` with an in-memory
heap-sort instead of a full external sort — but that's speculative until
there's real evidence it's needed, so it was not implemented.

## 11. Personal records — 30-day range, same exercise

Same query, `date` range added: `Nested Loop` →
`Index Only Scan using idx_entries_user_exercise_date` (`Heap Fetches: 0`,
fully covered by the index), joined to `workout_sets` via
`idx_sets_entry`. 420 matching entries / 1,680 sets, all three sorts done
in-memory (`Sort Method: quicksort`, no disk spill), 1,280 buffer hits,
**2.154ms**.

Interpretation: as expected — narrowing the candidate set via a date range
lets the composite index (which includes `date` as a trailing key) do an
index-only scan, and the much smaller candidate set (1,680 vs 80,000 rows)
avoids the disk-spilling sorts entirely. Confirms the same proportional-cost
model from a different angle: the range-bounded query is ~70x faster than
the all-time query specifically because its candidate set is ~48x smaller.

## 12. Write-path sanity check

Not a load test — a correctness/behavior check against the real Docker API
container with the perf dataset already present (50,002 entries for
`perf-user` at the time of the check).

- A valid 2-entry bulk `POST /workouts` returned `201` in ~52ms round-trip
  (HTTP + validation + DB transaction + serialization) and was independently
  verified via `psql`: both entries and all 3 sets present with correct
  normalized names and converted weights.
- A batch with one invalid entry (`weight: -50`) was rejected `400` at the
  DTO validation layer, before touching the DB — row count for `perf-user`
  was confirmed unchanged (`50002` before and after), i.e. no partial commit.
- `WorkoutsRepository.createMany` wraps entry + set inserts in a single
  `prisma.$transaction(...)`, so any DB-level failure mid-batch would roll
  back atomically; a DB-level failure couldn't be triggered through valid API
  input in this check (no reachable DTO-valid-but-DB-invalid path exists),
  so this specific claim rests on the existing transaction wrapper, not a
  freshly observed rollback.
- No indication that the four `workout_entries` indexes or three
  `workout_sets` indexes make ordinary writes noticeably slow — a 2-entry/
  3-set write completed in double-digit milliseconds including full HTTP
  round-trip, most of which is not DB time.

## 13. Index review

| Index | Scans (this session) | Verdict |
|---|---|---|
| `idx_entries_user_date` | 19 | Used — base case, cursor pagination, substring/muscle-group filters all route through it |
| `idx_entries_user_exercise_date` | 8 | Used — PR range-bounded query (index-only scan) |
| `idx_entries_exercise_trgm` | 2 | Used — PR all-time equality lookup, *not* used for substring search at this data shape (§7) |
| `workout_entries_pkey` | 201,350 | Used — FK/relation lookups, Prisma's default row identification |
| `idx_sets_entry` | 52,142 | Used — every sets-for-entry lookup |
| `uq_sets_entry_set_index` | 497 | Used — enforces set-index uniqueness per entry |
| `workout_sets_pkey` | 0 (this session) | Not read from in these scenarios, but structurally required (primary key) — not a candidate for removal |

No redundant indexes found. No evidence of a missing index — every scenario
either used an index scan/index-only scan appropriately, or (for the 7-row
`exercise_muscle_groups` table) correctly used a sequential scan because the
table is too small for an index to help. **No index or schema changes made**
— every query already routes through an appropriate index for its access
pattern at this data shape, and the one sub-optimal-looking behavior found
(deep-cursor pagination cost growing with depth, §6) doesn't cross into
"concrete problem" territory at the tested scale.

## 14. Regression check

No query or schema changes were made as a result of this step (all findings
were either confirmations of the existing cost model or sub-3ms costs not
warranting a change), so no BEFORE/CHANGE/AFTER evidence applies. The full
suite was still re-run for safety after touching the benchmark tooling:
112 unit tests, 44 integration tests, 64 e2e tests all pass; lint, build, and
`prettier --check` all clean.

## Limitations

- Single developer laptop, single Postgres connection, zero concurrent load —
  these numbers say nothing about behavior under concurrent request volume,
  connection pool contention, or realistic production hardware/network
  latency. No load test was run and no throughput ("requests/sec") number is
  claimed anywhere in this document.
- Only one user has a large dataset; multi-tenant index contention (many
  users each with tens of thousands of entries, interleaved writes) is not
  exercised.
- The 40%-concentration single-exercise scenario is deliberately worst-case,
  not representative of typical usage — it exists specifically to stress-test
  the PR query's candidate-set-proportional cost model.
- `pg_stat_user_indexes` scan counts reflect only this benchmark session
  (plus incidental test-suite activity), not real production traffic
  patterns — they indicate which indexes *can* be used for these query
  shapes, not their real-world hit rate.
- The write-path check exercised a small (2-entry) batch; behavior at the
  documented `MAX_BULK_ENTRIES` limit was not separately re-measured here
  (it was covered functionally, not for performance, in earlier steps).
